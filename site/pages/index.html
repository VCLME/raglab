Private RAG you can measure.

raglab answers questions from your documents without them ever leaving your servers. Every component is kept only if it improves the numbers on frozen benchmarks, scored by an independent, calibrated judge. When the answer is not in your documents, it says so.

Why it matters

Your data stays on your infrastructure

Documents, embeddings, the search index and the language model all run on your machines: PostgreSQL with pgvector, a local embedding model, Ollama for generation. No call to an external API, so contracts, patient files or case law never leave the building.

Quality is measured, not claimed

Two frozen question sets with passage-level ground truth: {{piaf_r5_v0}} Recall@5 on French Wikipedia at baseline, and a harder Brazilian-law set. Generated answers are scored by a judge from another model family whose reliability was itself measured.

It says when it doesn't know

The model is instructed to answer only from retrieved passages, cite each one, and reply with a fixed “not in your documents” message when the context is insufficient. Faithfulness at baseline: {{faith_piaf_v0}} on French questions.

The article-number problem

{{ref_r5_v0}}

Lawyers ask things like “what does art. 49 of Law 8.078 say?”. On 252 Brazilian federal laws, plain dense retrieval found the right passage in the top five only {{ref_r5_v0}} of the time for the {{ref_cases}} questions that cite an article number (baseline v0). The same system finds questions naming an acronym or entity {{entity_r5_v0}} of the time.

Embeddings capture meaning, not identifiers: “art. 49” and “art. 94” look almost the same to them. Adding keyword search (BM25) did not help ({{ref_r5_hybrid}}): it finds the right law, but article chunks only say “Art. 49”, like every other law.

What fixed it is a citation resolver: “art. N da Lei X” is parsed, the search is restricted to that law and the cited article is pinned first. Those questions went from {{ref_r5_v1}} to {{ref_r5_cites}} with the resolver alone, and {{ref_r5_full}} in the full pipeline.

How it's built

  • Passage-level benchmarks (phase 9.1): frozen PIAF and LexML question sets; a hit counts only if the retrieved chunk overlaps the exact answer passage.
  • Embedder cache: model loaded once; search latency {{latency_v0}} → {{latency_cache}} p50.
  • Complete top-k: pgvector iterative scan so a filtered search always returns k chunks; effect measuring (baseline v1).
  • Hybrid BM25 + RRF (9.2): a better candidate pool for re-ranking; article-number questions unchanged ({{ref_r5_hybrid}}).
  • Cross-encoder re-ranking (9.3): {{reranker_full}} re-reads the fused candidates; the largest single gain, and the largest cost (see limits). Details.
  • Citation resolver (9.3b): legal references parsed and resolved before search; article-number questions {{ref_r5_v1}} → {{ref_r5_cites}}. Details.
  • Hardened API (9.5): streaming answers, per-stage timeouts, request ids, optional API key, readiness checks.

Try it

Needs Docker. A GPU is optional (an override file enables it for Ollama). Every number on this site was measured on one laptop ({{gpu_full}}): {{generator_full}} and {{reranker_full}} share that card, and the judge model only loads once Ollama has been unloaded.

git clone {{repo_url}}.git && cd raglab
docker compose up -d postgres ollama adminer neo4j
docker compose --profile app up -d api frontend
docker compose exec ollama ollama pull qwen2.5:7b

Open http://localhost:8081, add a folder of documents under Expert → Corpus, build an index, then ask questions in Chat. The API is documented at http://localhost:8000/docs.

Limits

  • Benchmarked on two corpora (French Wikipedia, Brazilian federal law); your documents may behave differently, which is why the benchmark tooling ships with it.
  • LexML questions were written by a model, then filtered and spot-checked by hand.
  • Judge calibration covers French only, with synthetic errors: an optimistic bound on its reliability.
  • No OCR for scanned PDFs; ingestion and indexing run synchronously.
  • Re-ranking is the price of the gains: search takes {{latency_full}} p50 on PIAF ({{latency_full_lexml}} on LexML), against {{latency_v1}} for dense search alone. Measured on one laptop GPU; latency will differ on your hardware.

What I'd do next

  • Cut re-ranking latency: candidate count, input length and batch size have not been swept yet.
  • Query routing and calibrated abstention (phase 9.4), measured on 80 unanswerable questions.
  • Observability: Prometheus metrics, Grafana dashboard, drift report (9.6).
  • Weekly quality gate that fails when retrieval regresses (9.7).
  • Run the benchmark on a client's own documents before any deployment.
