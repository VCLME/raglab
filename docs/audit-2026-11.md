# Audit et plan d'action — 3 novembre 2026

État du projet à la fin de la phase 9.3b, ce qui est solide, ce qui s'éparpille, la thèse à tenir, et le plan pour y arriver. Les chiffres viennent de `benchmarks/results/` et de la base locale ; rien n'est estimé.

## 1. Où en est le projet

**Fusionné dans `main`** : baseline reproductible (9.1), recherche hybride BM25 + RRF (9.2), re-ranking cross-encoder avec garde-fou GPU (9.3), résolveur de citations juridiques (9.3b), API durcie (9.5), observabilité Prometheus + Grafana (9.6), portes de qualité `raglab gate` (9.7), CI complète (ruff, mypy, pytest, tsc, Playwright, builds Docker), site GitHub Pages public, licence MIT.

**Ouvert** : refonte de l'interface + fournisseurs LLM compatibles OpenAI (#45, deuxième série de retours en cours), site vitrine au style du portfolio (#42), routeur et abstention (#35, brouillon, à remesurer), page Bases de données (#25, ancienne, à remettre sur `main`), correctif de langue des réponses (mesure GPU en cours).

**Mesuré** (jeux figés : PIAF 500 questions fr, LexML 277 questions pt sur 252 lois fédérales) :

| | Baseline v1 | Pipeline complet |
|---|---|---|
| LexML Recall@5 | 0,466 | **0,816** |
| Questions citant un numéro d'article | 9 % | **72 %** (+61 / −0, p < 0,001, vérifié sur 72 questions jamais regardées) |
| PIAF Recall@5 | 0,878 | **0,966** |
| Justesse des réponses LexML | 0,45 | **0,60** |
| Fidélité LexML | 0,90 | 0,90 |
| Latence de recherche p50 | 23–41 ms | 537–733 ms (re-ranking ~0,5 s) |

**Taille** : 359 tests Python, 4 suites Playwright, 12 pages Expert + Chat + mode pédagogique, 16 fichiers de docs (3 000 lignes), un rapport LaTeX, 11 runs de benchmark versionnés.

## 2. Ce qui est solide

Ce sont les quatre choses qui ont de la valeur sur un portfolio ; tout le reste doit les servir.

1. **Le protocole de mesure.** Questions figées, corpus entier indexé, pertinence au passage (la bonne loi mais le mauvais article est un échec), juge indépendant calibré (Gemma 4 : 97,8 % de détection des détails inventés), tests appariés (McNemar, bootstrap), chaque run enregistré avec sa commande, son commit et son matériel. Peu de projets RAG publics ont ça.
2. **Le résolveur de citations.** C'est l'exemple type de l'histoire qu'on veut raconter : un RAG classique échoue sur « art. 49 da Lei 8.078 » (9 %), on le mesure, on comprend pourquoi (les embeddings brouillent les identifiants, BM25 trouve la loi mais pas l'article), on corrige, on remesure (72 %), on vérifie sur des questions jamais vues.
3. **Le pipeline par défaut mesuré, 100 % local sur 8 Go.** Hybride + re-ranking + citations, latence connue, VRAM connue (7,6 Go au pic), repli propre sans GPU.
4. **Le mode pédagogique.** Le pipeline en direct, avec les vrais rangs, les vraies formules et le vrai code : c'est ce qui distingue le projet d'une démo de plus.

## 3. Ce qui s'éparpille

- **Le visiteur ne sait pas quoi faire.** Il arrive sur un Chat vide avec un sélecteur de corpus sans description. Rien ne lui montre ce que raglab fait de mieux qu'un RAG classique.
- **Douze pages Expert, dont plusieurs sans mesure ni lien avec la thèse** : Graph (Neo4j avec extraction d'entités par LLM, jamais mesuré), Playground, LexML (chargement), Ollama, Ingest. Les stratégies de découpage `slide` et `late` sont proposées dans l'UI mais n'ont jamais été mesurées sur les jeux figés.
- **Deux « graphes » en concurrence** : le store Neo4j actuel (chunks + entités) et le graphe structuré envisagé pour 9.9. Il faut en garder un.
- **Docs sans entrée** : 16 fichiers sans index, un rapport LaTeX dont les chiffres datent d'avant 9.2, une roadmap qui mêle les phases 0 à 9.
- **Des mesures partielles, à assumer** : juges RAGAS sur 100 questions par jeu ; calibration du juge en français seulement, avec des erreurs fabriquées ; justesse LexML à 0,60, plafond du modèle 7B ; routeur mesuré sur l'ancien pipeline.
- **Dettes** : adresse e-mail personnelle dans l'historique git (180 commits), mots de passe de développement dans `docker-compose.yml`, corpus orphelins en base (`piaf_fr`, `lexml_real`), 5 bases de test, 21 worktrees, #25 en attente depuis le début de la phase 9.

## 4. La thèse

> **Le RAG classique échoue sur les documents structurés, référencés et versionnés — lois, contrats, normes. raglab montre où, le mesure, et le corrige brique par brique, entièrement en local.**

Sur un corpus de lois, un RAG classique échoue de quatre façons. Chacune a (ou aura) son jeu de questions, sa mesure avant/après, et sa brique.

| # | Mode d'échec | Exemple | État |
|---|---|---|---|
| 1 | **Identifiants** : les embeddings brouillent les numéros | « art. 49 da Lei 8.078 » → l'art. 94 | Mesuré et corrigé : 9 % → 72 % |
| 2 | **Renvois** : la réponse est dans l'article cité, pas dans celui qui est trouvé | « quelles peines pour l'art. 5 ? » → les peines sont à l'art. 12 | À mesurer. 1 420 articles sur 4 055 renvoient à un autre article (3 015 renvois) ; 115 liens entre lois |
| 3 | **Versions** : un texte abrogé ou réécrit est cité comme en vigueur | « (Revogado) », « Redação dada pela Lei nº 14.026 » | À mesurer. 70 lois sur 252 ont des articles réécrits (863), 79 ont des articles abrogés (1 084 mentions), 1 239 articles insérés |
| 4 | **Hors périmètre** : le modèle répond quand même | question sur le droit français posée à un corpus brésilien | Mesuré sur l'ancien pipeline : précision 0,984, rappel 0,75 (routeur 9.4) |

Le corpus est déjà le bon : du vrai droit, public, dans une langue que les embeddings gèrent moins bien que l'anglais, avec les trois structures qui piègent un RAG. Il n'y a pas besoin d'en changer, mais de mesurer les deux modes d'échec qui ne le sont pas encore.

Pourquoi ça porte : les clients qui ont ces documents (juridique, conformité, industrie réglementée, assurance) sont ceux qui ne peuvent pas envoyer leurs données à une API — d'où le « 100 % local ».

## 5. Décisions proposées

| Question | Décision | Pourquoi |
|---|---|---|
| Graphe : où ? | Dans **Neo4j, sur le chemin des requêtes**, comme troisième branche de recherche en parallèle de la recherche dense et de BM25, fusion RRF à trois sources, puis re-ranking. Optionnel : sans Neo4j, la branche est sautée et la réponse le dit (comme le re-ranking sans GPU). | C'est ce que le projet annonce (hybride vecteurs + texte + graphe), Neo4j est déjà dans le compose, et les requêtes Cypher sont lisibles dans le mode pédagogique. |
| Graphe : quel schéma ? | Une seule base (Neo4j Community n'en a qu'une), un socle commun `Document → Section → Chunk` (`PART_OF`, `NEXT`), et un profil par type de document. Lois d'abord : `Law`, `Article`, `CITES`, `AMENDS`, `REVOKES`, extraits par règles (les mêmes que le résolveur de citations), sans LLM. | Les renvois juridiques sont explicites dans le texte : un modèle qui les devinerait coûterait plus cher et serait moins fiable. |
| Le store Neo4j actuel (entités par LLM) | Retiré du pipeline et de l'UI par défaut, gardé derrière un flag Expert jusqu'à ce que 9.9 le remplace. | Jamais mesuré ; deux graphes concurrents brouillent le message. |
| Un modèle qui choisit « graphe ou vecteurs » par document ? | Non. Tout tourne en parallèle, le re-ranker arbitre. Le routeur 9.4 pourra plus tard sauter une branche inutile. | C'est le schéma standard (Neo4j GraphRAG, LlamaIndex) ; ici chaque branche coûte quelques ms. |
| Plusieurs corpus en parallèle ? | Pas d'union de corpus. Le routeur (#35) choisit le corpus selon la langue et l'intention ; le sélecteur affiche une description par corpus (langue, nombre de documents, pour quoi il est bon, questions d'exemple). | Les benchmarks restent par corpus, et la comparaison des stratégies aussi. |

| Stratégies de découpage | Ne pas les modifier ; les **mesurer** (`slide`, `late` contre `traditional`, recherche seule, ~30 min de GPU). | L'UI les propose : il faut un chiffre derrière, sinon c'est un bouton de plus. |
| Abstention | Seuil « point A » (prudent), remesure sur le pipeline complet. | Déjà choisi par le propriétaire. |
| #25 (page Bases de données) | Remettre sur `main` et fusionner : boutons Adminer et Neo4j Browser en Expert. | Demandé, et utile pour montrer le graphe. |
| E-mail dans l'historique | Accepter (choix habituel sur un portfolio) ou masquer pour la suite via l'adresse `noreply` GitHub. Ne pas réécrire l'historique. | Réécrire casse les PR et les liens. |

| Rapport LaTeX | Régénérer les chiffres à la fin de 9.9, pas avant. | Sinon il sera périmé deux fois. |

## 6. L'expérience utilisateur visée

Deux publics, deux parcours.

**Le visiteur (2 minutes)** : site → « Essayer » → Chat en **mode Démo**.
- Un sélecteur de corpus avec description.
- Quatre questions pièges pré-remplies, une par mode d'échec.
- Un bouton **« Comparer : RAG classique / raglab »** qui affiche côte à côte les deux réponses et leurs passages (dense seul, sans re-ranking ni citations, contre le pipeline complet). C'est la fonctionnalité qui matérialise la thèse ; elle ne coûte presque rien, tous les réglages existent déjà dans l'API.
- Le mode pédagogique explique la différence, étape par étape.

**L'ingénieur (20 minutes)** : Expert → Benchmarks (lancer, comparer des runs), Retrieval (scores intermédiaires), Index (stratégies mesurées), Graph (Neo4j), Bases de données (Adminer, Neo4j Browser), Observabilité (Grafana).

Ce qui se range : Playground, Ollama, LexML, Ingest deviennent une section « Outils » en bas du menu Expert, ou fusionnent (Ingest + Index + Corpus = « Corpus »).
